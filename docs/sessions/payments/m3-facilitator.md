# M3 part A: the facilitator, the shop's 402 API and the recorder (T1 Payments working notes)

Part A is the code and its tests, offline and on an anvil fork of Whitechain Sepolia against the real deployed checkout, the real test USDT and Permit2. Part B (real payments as `rehearsal.vitalik`, the subscription demo, C7 as `acceptance.vitalik`) waits for T2's M5 and M6. The hosted routes are M4.

## What is built

- `packages/facilitator` (`@graphpay/facilitator`):
  - `wire.mjs`: zod schemas for the requirement, the payload and the order, every field length-capped; 32-byte fields lower-cased on the way in.
  - `client.mjs`: the payer's `SchemeNetworkClient`: signs the Permit2 witness over the order and, while the payer's Permit2 allowance is short, a bounded EIP-2612 approval (50 test USDT or the amount), so the first payment needs no gas and no earlier transaction. It refuses a requirement for another token or network, and honours x402Client's resolved spend cap.
  - `pipeline.mjs`: the five stages of `planning/SPEC/PAYMENTS_WHITECHAIN.md` §5 in order. Stage 1 (free): schema, scheme and network, the token in the requirement and the permit, our contract, the merchant allow-list, payTo = order merchant, amount = order = permit, permit nonce = order id, the deadline, the name hashes to the payer node. Stage 2, by Permit2's own rule (`SignatureVerification.verify` branches on the payer's code): a wallet without code must give exactly 65 bytes with v 27 or 28, recovered locally; a wallet with code (a contract, or an EOA with an EIP-7702 delegation) is asked `isValidSignature` with the bytes as they are; ERC-6492 and ERC-8010 wrappers refused (viem's helpers accept all of these, so they are not the rule); then the ENS gate (agents only; 20 s cache by exact spelling, stamped before the read, fail closed; our own read failure is refused but never recorded). Stage 3: the gate's ENS epoch must equal the on-chain policy's, order status, Permit2 nonce bit, balance, allowance or an approval that will really apply (value, deadline, 65 bytes with v 27/28 and a low s, a wallet without code, signer against the token's current nonce), and the contract's policy check predicted (`predictPolicy`, the same order as `_checkPolicy`). Stage 4: send only if all pass; a predicted revoked, expired or over-cap failure goes on-chain only within the daily quota (20) and at most once per order; `NODE_MISMATCH` never. Stage 5, at send time: global, per-payer (10/min) and per-payee (30/min) limits checked first and consumed only when everything passed, a reverting estimate refused (`simulation_failed`), the 450k gas cap, gas sent as `min(cap, max(1.2 × estimate, 400k))`, the daily gas budget reserved and corrected from the receipt, the relayer floor, the receipt timeout, and a deadline that leaves room for it. `settle` runs one at a time through a queue of 20 and decides from the receipt; an order already sent and undecided is never sent again (a retry waits on the same hash; after a send that errored, `in_flight` for a minute).
  - Refusal records: only for a proven payer (after the signature), once per order, payer and reason, rate-limited per payer and per instance, fired and never awaited; attributed to the agent's name only when `nodeOfWallet(payer)` is that node (looked up off the decision path when the refusal came before the chain reads), with the epoch; otherwise written from the wallet's reverse name.
  - `http.mjs`: Fetch-API handler: bearer (constant time, at least 24 characters) on `/verify` and `/settle`, 64 KB counted on the bytes read, 429 on rate limits, 503 while the start-up checks fail (retried on the next call), `/health` cached 5 s (signer, balance, budget, floor, quota, queue), `/supported` free; errors are one line with the error's name only.
  - `startup.mjs`: chain 1874, `checkout.USDT()` = the configured token, the configured EIP-712 domain = the token's `DOMAIN_SEPARATOR()`, the ENS RPC on 11155111; `ALLOW_REAL_NETWORK=1` for any non-loopback RPC (exact host match), never the ENS stub on a real network, https when hosted; errors name the check, never the RPC's message.
  - `recorder.mjs`: the route handler for `/api/recorder/attempts` (bearer, 503 until the W_SYNC writer is configured, strict schema) and `attemptEdge`, the input to T3's `recordEdge`: one readonly `fail` edge, ref `att:<orderId>:<wallet>:<reason>` (a replay is the same edge), the wallet also in the payload; the route refuses a name that does not hash to the node.
  - `settings.mjs`: env settings (§9) checked against `@graphpay/config`: the checkout, the token and its EIP-712 domain, Permit2 and the ENS root from the config, a repeated env value must equal it; strict limits; secrets of at least 24 characters, never in a message; the merchant lists from env until the config holds the public role addresses (then they must equal it).
  - `client.mjs` pins the configured checkout: a 402 naming another contract is refused before signing.
- `packages/shop` (`@graphpay/shop`): the stateless shop API of §6 as a Fetch-API handler. Catalog and prices from the story config only, labelled synthetic; a free quote that writes nothing; order ids hashed from the terms with the top bit cleared, an echoed `exp` clamped to now + 10 min (plus 30 s of clock slack); `X-Demo-Passcode` (constant time, at least 24 characters, spending off without one) on the pay and re-order steps; the payee must equal `resolvePayee(<shop name>)` (cached 20 s) or the step answers 503 with no 402; `alreadyPaid` from the chain; a re-order only after a paid parent of the same buyer at the same shop; the quote written to Arkiv first when the 402 step carries a `requestId` (key in `extra.quoteKey`; a failed write is a 503); 402 with exactly one `accepts` entry, identical in the header and the body; facilitator outage → 502; a refusal or on-chain failure → 402 with `PAYMENT-RESPONSE`; a receipt timeout → 504 and a send in flight → 503, so the payer treats them as unsettled (T4's G16 rule); `markDelivered` with the merchant key when configured; the pay route and the quote writes are rate-limited per instance.

## Deviations and choices

- Prices are per pack in the story (`priceMicro` for `quantity` pieces); a quote names pieces and is priced `ceil(priceMicro × qty / quantity)`, the same rule T4's buyer and mock shop use. The catalog adds `unitPriceMicro` when it divides exactly. `stock` is `null` unless the story gives one (no invented numbers).
- The quote's terms carry the sku; the order id hashes `(shopNode, buyerNode, payerNode, wallet, sku, qty, exp, parent)`; an agent's wallet is optional (zero address), a human payer's is required.
- `verify` does not estimate gas: the send-time checks (gas cap, budget, floor, simulation) run in `settle` only.
- The hosted routes (`apps/web/app/api/{shop,facilitator,recorder}`) and the env wiring are M4; the packages take every dependency by injection.
