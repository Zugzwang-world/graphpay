# How GraphPay uses Arkiv

Each row is an Arkiv feature, something a person sees because of it, and where it is in the code. "Shipped" means it runs against Arkiv Rabdi (chain 7794095) in this repo and on the live site; "built" means the code and tests exist and no screen calls it yet. The synthetic city is labelled synthetic wherever it appears. The entities are in [`schema.md`](schema.md). Drafted by T3 on Fri 6 Nov; finished by the Submission stream (W7) that night, with each state checked against the live site.

The generic part is a package anyone can install: [`@graphpay_ethglobal/arkiv-graph`](https://www.npmjs.com/package/@graphpay_ethglobal/arkiv-graph) (MIT; source in [`packages/arkiv-graph`](../packages/arkiv-graph); its README has a five-minute quickstart that runs in memory and a leaderboard example with no payments in it). GraphPay's own model sits on top of it in `packages/money-graph` and uses the package only through its public exports. What anyone can reuse is in [`reach.md`](reach.md); why we chose Arkiv over a database of our own is in [`why-arkiv.md`](why-arkiv.md).

## What we did not use

- **`watchEntityEvents`.** We do not subscribe to entity events. The mirror polls Whitechain by block and the website reads Arkiv on request (ADR-0055), so there is no live-push row in the table. We did not test the watch path.
- **Entity ownership changes** and **`ExpiryExtended` events.** Not needed.

## Why this shape

Arkiv has no SUM, GROUP BY or join (see [`friction.md`](friction.md)), and a question like "which shops sold most" would otherwise mean reading every payment. So the graph layer writes **tallies** with each payment and keeps them in step by one atomic batch. On the live testnet with a synthetic city of 490 payment and renewal rows, the city-wide top 10 takes 2 reads against 5 for plain code reading one page at a time (6 with every page in flight); on other questions Graph Arkiv ties or needs more reads, and we say so. It is decentralized, secure and verifiable: the rows are public on Arkiv, a reader checks each row's owner, and the explain trace shows every query.
