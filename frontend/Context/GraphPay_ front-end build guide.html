Build the GraphPay demo website

A guide for the front-end team. Two phone apps (the customer and the shop) and an “under the hood” panel, side by side on one website. Every button works: first against mock data, then against our live agents, ENS, Arkiv and Whitechain. Read this with FRONTEND_HANDOVER.md, which holds the full spec.

Seven rules that keep this easy to wire up later

  • One contractComponents talk only to the DemoAdapter. No direct network calls. That’s how mock becomes live in one setting.
  • Story from a fileNames, shops, products, prices, prompts and images come from story.json. The story changes Friday morning; the UI must not.
  • Every button worksEach one triggers a visible result on the mock adapter. No dead clicks for judges.
  • Honest statesShow a “Mock data” badge in mock mode. Never present a fake transaction link as real.
  • Own designsBorrow flow patterns (an order timeline, a refund wizard), never code, assets or screens from other apps.
  • No secrets in the browserNo keys in front-end code. Spending sits behind the demo passcode, enforced by the backend.
  • Small pull requestsOne screen or one journey per PR, CI green, changes inside apps/demo-ui only. Claude Code’s own website lives in apps/web; leave it alone, we compare and combine later.

The contract

The only line between your UI and everything else: apps/demo-ui/src/demo/contract.ts. You build against the mock version; the backend team ships the live one. Changes to this file need both sides to agree.

Mock first, live later. The mock adapter plays scripted journeys from story.json with realistic delays (agents think 1–3 s, payments settle 2–4 s). The live adapter streams the same events from our backend. A single mode setting switches between them.

        Working with Claude

        Claude Code (or any AI coding tool) can build most of this quickly if you give it the right inputs and keep requests small. This is a way of working, not a script.

        How to work

        • Open Claude Code inside the repo, in your own branch. At the start of each session, point it at FRONTEND_HANDOVER.md, contract.ts and story.json.
        • Ask for one screen or one journey at a time: presentational components, plus a hook that reads from the adapter.
        • Ask for every state: loading, empty, success, refused with a reason, error with retry, and the mock badge.
        • Close the loop visually: run the app, take a screenshot (or let Claude use the browser tools), and ask for specific fixes.
        • If Claude wants to change contract.ts or add a backend call, stop and check with the founder first.
        • Your prompts are logged automatically in this repo. That’s part of our AI disclosure, so write them as you’d want a judge to read them.

        Example requests

        Check every pull request for

        • No names, prices or addresses typed into components.
        • No network calls outside the adapter.
        • Every button does something visible on the mock.
        • Works at 390 px wide and on a projector.
        • Keyboard focus is visible; every button says what it does.
        • The mock badge shows in mock mode.
